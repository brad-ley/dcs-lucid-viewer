Standard User Operations

Step-by-step checklist for a typical ATX245S acquisition session

Full software reference: User Manual ↗  |  Hardware details: ATX245S Camera Manual ↗

1 — Startup & Camera Connection

  • Launch the Lucid Camera Acquisition Tool. The camera list may populate automatically. If it is empty or you have just powered the camera on, click the Refresh button next to the camera dropdown to re-scan the network.
  • Select the ATX245S entry from the camera dropdown. The serial number is shown in the list; confirm it matches the unit physically connected.
  • Click Connect. The status bar should show a successful connection message and the parameter controls will become active.
  • After a camera power cycle, the camera boots with the DCS preset loaded. You must reload your custom configuration manually — see Section 8 — Config Persistence. Do this before adjusting anything else, so your saved settings are the baseline.

2 — Preview & Focus

  • Click the Preview button on the main window. A separate, non-blocking preview window opens — the main window stays fully interactive.
  • Click Start Preview in the preview window to begin the live camera stream. You should see the live image within a second or two.
  • Use Auto Contrast (bottom bar, or Auto-contrast → Enable in the menu) to automatically stretch the display range. This makes it much easier to judge focus before the exposure and gain are finalized.
  • Focus adjustment is done remotely via the motorized focus controller. Connect via Remote Desktop to the focus laptop:

    IP: xxx.xxx.xxx.73  |  Username: Detector-B  |  Password: (usual lab password)

    Adjust focus while watching the live preview in the acquisition software. Use ROI → Open Focus Diagnostic to open a quantitative focus metric plot — draw a small ROI over a sharp feature in the scene and maximize the metric value.
  • Left-click any pixel in the preview image to pin a count readback overlay showing the raw sensor value at that position. Useful for checking exposure level on a specific region.
  • Verify that no large areas are saturated (red overlay) or dead-pixel yellow — adjust ExposureTime and/or Gain to bring the histogram into a comfortable range.
Tip: Zoom with the scroll wheel, pan by dragging, and double-click to fit-to-window. Right-click the Draw ROI button to reset the ROI back to full frame if needed.

3 — Configuring for Maximum Frame Rate (82 Hz)

The ATX245S sensor can deliver up to 82 Hz frame rate, but only if the total data throughput is reduced to roughly ¼ of the full-frame data rate. The interface link (10GigE) is the bottleneck, not the sensor. Use any combination of the following levers — the product of their reductions must reach ~¼:

Lever How to set it Throughput effect
Pixel bit depth Set PixelFormat to Mono8 instead of Mono12 or Mono16 12-bit → 8-bit: ×0.67; 16-bit → 8-bit: ×0.50
ROI crop Draw an ROI in the preview window or set Width / Height / OffsetX / OffsetY directly Proportional to area fraction — e.g. ½ width × ½ height = ×0.25.

Row reduction is what matters most. CMOS sensors read out row-by-row, so reducing Height directly shortens the readout time and raises the maximum frame rate. Reducing Width only lowers the data volume on the link — it does not shorten readout. Prioritize a narrow strip (fewer rows) over a narrow column (fewer columns) when the goal is maximum frame rate.
Binning / Decimation Set BinningHorizontal and BinningVertical (or DecimationHorizontal / DecimationVertical) in Advanced 2×2 binning = ×0.25 pixels transmitted
Example path to 82 Hz: 2×2 binning alone reduces throughput to ¼ and is the simplest single setting. Alternatively, a ½-height ROI combined with Mono8 (vs Mono12) achieves a similar reduction while preserving spatial resolution in one axis.
  • Open Advanced Parameters and set BinningHorizontal and BinningVertical to 2 (or crop the ROI to the required area), then adjust PixelFormat as needed.
  • If using external triggering (typical): leave AcquisitionFrameRateEnable false (the default). In this state AcquisitionFrameRate is a read-only node that reports what the frame rate would be for internal triggering — i.e. the sensor's current maximum given the active resolution and bit depth. The camera will accept trigger pulses up to that ceiling; your external trigger just needs to be a few Hz slower than this reported value to guarantee every pulse is captured.

    If using internal triggering: set AcquisitionFrameRateEnable to true first — this unlocks AcquisitionFrameRate for editing — then set it to 82 (or the desired value). If the camera rejects the value, the current resolution / bit depth still exceeds the link budget; reduce further.
  • Set ExposureTime to a value shorter than one frame period (1 / 82 Hz ≈ 12,200 µs). A safe margin is leaving at least 4 ms of dead time, so ≤ 8,000 µs at 82 Hz. You need way less than this, as the e-beam pulse length is only 200 ps and the scintillator decays with a lifetime of tens of nanoseconds.
  • Click Apply Pinned Parameters on the main window and verify the frame rate in the preview status bar matches the target.

4 — Trigger Setup

The camera operates in hardware trigger mode for synchronized acquisition. Each frame trigger comes from an external signal (e.g., from the oscilloscope or a function generator). The camera also outputs an Exposure Active signal on a GPIO line that goes high for the exact duration of each frame's integration period.

  • Confirm TriggerMode is set to On (in the pinned parameters or via Advanced). When trigger mode is on, the Start Acquisition button label changes to Start Streaming — the camera arms and waits for hardware pulses rather than free-running.
  • Confirm TriggerSource is set to the correct GPIO line (e.g., Line0 or Line2 — check which line your trigger cable is physically connected to).
  • Confirm TriggerActivation matches your signal (typically RisingEdge).
  • Verify the Exposure Active output line assignment in Advanced (LineSelector → select output line → LineSource = ExposureActive). Connect this output to a scope channel for timing reference.
Event trigger timing: Each frame carries a LineStatusAll chunk field that records whether the event trigger input (e.g., the stimulus signal from your experiment) was high or low at the moment the frame was captured. By combining:
  • the frame's line_status_all bit (informs on whether the event was active?)
  • the oscilloscope-measured time difference between the event trigger and the subsequent camera frame trigger pulse
you can determine the precise sub-frame timing of the event relative to any acquired frame. See Scope & Timing below for the analysis workflow.
Chunk data must be enabled for line_status_all to appear in frame_data.csv. In Advanced Parameters, set ChunkModeActive = true, then enable individual chunk selectors (ChunkSelector = LineStatusAll → ChunkEnable = true, and repeat for Timestamp, Gain, ExposureTime). Should be already set in your Custom config.
Exposure delay and laser phase alignment: The HHLC chopper opens at 82 Hz, which is the Jülich 987 Hz reference signal divided by 12. The camera must be phased to sync with the HHLC opening before data acquisition. Two approaches:
  • Camera-side delay: set TriggerDelay (in the pinned parameters or Advanced) to shift the start of the camera exposure window by the required number of microseconds. TriggerDelay has single-µs precision and is the preferred method when only small adjustments are needed.
  • Source-side phase: adjust the Jülich Chopper phase via the Laser FPGA control to align the 82 Hz output pulse with the desired point in the camera's integration window. Use this approach when sub-µs precision is needed.
Confirm alignment by monitoring the Exposure Active GPIO output (camera exposure is low) the oscilloscope along with the B-station slow photodiode signal. Once phased, it is possible to reduce the exposure time lower to ensure it is only signle bunch per frame.

5 — Verify Pinned Settings

Before every acquisition, review the pinned parameters panel on the main window. The most critical items are listed below. See Pinned Parameters Reference for a full description of each setting.

  • TriggerMode = On — required for hardware-synchronized acquisition.
  • AcquisitionFrameRateEnable is false (typical for external triggering). In this state AcquisitionFrameRate is read-only and reports the sensor's current maximum — verify this value is a few Hz above your intended trigger rate so every pulse is accepted. If it is too low, reduce resolution, bit depth, or binning until the ceiling rises above your trigger rate.
  • ExposureTime is shorter than the frame period with adequate margin.
  • ExposureTimeAuto and GainAuto are Off. For scientific experiments each frame must integrate for exactly the same duration at the same gain — auto-exposure or auto-gain will vary brightness between frames and corrupt quantitative analysis.

    Gain regime: Gain ≤ 24 dB keeps the sensor in its low-gain (analog) regime, which preserves the full well capacity and gives the best dynamic range. Gain > 24 dB switches to a digital multiplier that amplifies read noise along with the signal — avoid it unless the scene is extremely dim and dynamic range is not a concern.
  • PixelFormat matches the bit depth you intend to record (affects file size and post-processing pipeline).
  • Width, Height, OffsetX, OffsetY define the active ROI. Confirm the region is correct in the preview window (green overlay).
  • Output folder is set, has a meaningful acquisition name (or leave blank for auto-name and -timestamp), and the drive has sufficient free space.

    Save to the D:\ drive. The D: drive is a Samsung 990 PRO NVMe SSD with a sustained write speed of ~6 GB/s — well above the ~1.5 GB/s needed for 82 Hz Mono12 acquisition. The C: drive (OS drive) is significantly slower and should not be used for data.

    Rough size estimate: frames × width × height × (bits/8) bytes. At 82 Hz for 10 s with a 2664×2304 cropped frame at Mono12 (stored as 2 bytes): 820 × 2664 × 2304 × 2 ≈ 8.2 GB — verify free space before starting (the camera will warn the user if there is not sufficient space for an auto-stop acquisition or <50 GB for a manual acquisition).
  • If using Auto-Stop, confirm the timer duration is correct: Config → Auto-Stop Acquisition. The Stop button will show the countdown as soon as acquisition starts.

6 — Running Acquisition

  • Optionally click Notes… and enter a brief description of the run (sample, conditions, event type). These notes are saved in metadata.json alongside the frames.
  • Click Start Streaming (trigger mode) or Start Acquisition (free-run mode). The preview window pauses automatically.
  • Deliver your experiment / event trigger. The frame counter increments as frames arrive. The acquisition runs until you click Stop or the auto-stop timer fires.
  • After stopping, the log prints the complete save path: "Acquisition finished — N frames saved to: 'D:/.../[name]_...". Note or copy this path for post-processing.
  • Each acquisition folder always contains: metadata.json, frame_data.csv, camera_settings.json, and the image files. Verify the frame count in the log matches expectations before moving on.
File format note: Images are saved as .raw files — a direct binary stream of pixel values with no header, written at maximum speed to minimize I/O overhead. They cannot be opened directly in standard image viewers. Use the Python snippet in the User Manual → Raw Sequence section to load them, or ImageJ with the correct import settings (width × height × bit depth from metadata.json).

7 — Capturing Background Fields

Background correction removes fixed-pattern noise (dark current) and illumination non-uniformity (flat-field). The standard formula applied in post-processing is:

corrected = (data − dark) / (white − dark)

  • Dark field: Block all light reaching the sensor (lens cap or shutter). Go to Tools → Capture White/Dark Field and capture the dark field. This measures the camera's thermal / electronic offset at the current exposure and gain settings.
  • White field: Illuminate the scene uniformly (remove sample, use a diffuser or blank slide). Capture the white field from the same menu. This measures the illumination pattern and pixel-to-pixel sensitivity variation.
  • Both fields are saved as averaged images in the output folder. Capture them at the same ExposureTime, Gain, PixelFormat, and ROI as your data — the correction is meaningless otherwise.
  • If acquisition conditions change (different exposure, different ROI), recapture both fields.
Tip: Capture the white field before placing the sample, and capture the dark field without moving anything else — stray light or mechanical shift between the two captures introduces residual error.

8 — Saving and Loading Camera Configuration

Camera settings are not retained across a power cycle by default — the camera boots with the Custom settings preset. Use the custom config workflow to restore your working configuration reliably.

  • After configuring all camera parameters, go to Advanced → Save Custom Config…. This writes the full GenICam node snapshot to a .json file and to the camera's on-board user preset memory simultaneously.
  • After every camera power cycle, go to Advanced → Load Custom Config… and select the saved .json file to restore all settings. Do this immediately after connecting — before adjusting any parameters.
  • Note: every acquisition automatically saves a camera_settings.json snapshot alongside the data. This serves as a permanent record even if the preset is later overwritten, and can be loaded via Load Custom Config… to reproduce the exact conditions of a past session.
Important: After a power cycle, connect to the camera and load your Custom config before opening the preview or starting any acquisition. If you start with the Custom settings preset, the trigger mode, frame rate, ROI, and pixel format will all be at factory defaults — not your experiment settings.

Data Parsing Reference

Raw files and TIFF stacks written by this software contain camera-native pixel data. The correct loading strategy depends on pixel_format in metadata.json. The table below maps every format to its on-disk layout.

Format Summary Table

pixel_format Bits / pixel Bytes / pixel NumPy dtype Value range Notes
Mono8 8 1.000 uint8 0–255 Trivial; directly loadable.
Mono12 12 2.000 uint16, LE 0–4095 One pixel per 16-bit word; upper 4 bits are zero.
Mono16 16 2.000 uint16, LE 0–65535 Full 16-bit; directly loadable.
Mono12p 12 1.500 — 0–4095 PFNC LSB-first. 3 bytes per 2 pixels. Requires unpacking (see below).
Mono12Packed 12 1.500 — 0–4095 Lucid MSB-first. 3 bytes per 2 pixels. Same size, different nibble order (see below).
Mono10p 10 1.250 — 0–1023 PFNC LSB-first. 5 bytes per 4 pixels. Requires unpacking (see below).
Mono10Packed 10 1.250 — 0–1023 Lucid MSB-first. 5 bytes per 4 pixels, different layout (see below).
RGB8Packed 24 3.000 uint8 0–255 per channel 3-channel BGR interleaved; reshape to (H, W, 3).
BayerRG8, BayerGR8, … 8 1.000 uint8 0–255 Raw Bayer mosaic; demosaic with cv2.cvtColor or equivalent.
bytes_per_frame is exact for all formats. Packed formats (Mono12p, Mono12Packed, Mono10p, Mono10Packed) report the true packed byte count (bits_per_pixel × width × height) / 8; non-packed formats report ceil(bits_per_pixel / 8) × width × height. You can use bytes_per_frame directly to seek to a specific frame in a raw video file.

TIFF Files

TIFF stacks (stack.tiff) contain the camera's native bytes written directly into TIFF pages — packed formats are not automatically decoded. Field-capture TIFFs (white_field_mean.tiff, dark_field_mean.tiff) are always fully decoded to uint16 (or uint8 for 8-bit) because the field capture pipeline accumulates values in a 32-bit integer array before saving.

Use tiff_pixel_format from metadata.json ("uint8" or "uint16") to confirm the TIFF type. For field TIFFs, this is always the correct decoded dtype.

Python — Universal Loader

The function below dispatches on pixel_format and returns a (height, width) uint16 array for all mono formats:

import numpy as np import json def load_raw_frame(path, meta): """Load a single .raw frame. meta is the parsed metadata.json dict.""" width = meta["width"] height = meta["height"] fmt = meta["pixel_format"] bpp = meta["bits_per_pixel"] raw = np.fromfile(path, dtype=np.uint8) # ── Non-packed formats ───────────────────────────────────────────────── if bpp == 8: return raw.reshape(height, width) if fmt in ("Mono12", "Mono16"): # Little-endian uint16; values already in correct range return raw.view(np.uint16).reshape(height, width) # ── Mono12p (PFNC LSB-first, 3 bytes → 2 pixels) ────────────────────── if fmt == "Mono12p": b = raw.reshape(-1, 3) b0 = b[:, 0].astype(np.uint16) b1 = b[:, 1].astype(np.uint16) b2 = b[:, 2].astype(np.uint16) p0 = b0 | ((b1 & 0x0F) << 8) p1 = (b1 >> 4) | (b2 << 4) out = np.empty(height * width, dtype=np.uint16) out[0::2] = p0 out[1::2] = p1 return out.reshape(height, width) # ── Mono12Packed (Lucid MSB-first, 3 bytes → 2 pixels) ──────────────── if fmt == "Mono12Packed": b = raw.reshape(-1, 3) b0 = b[:, 0].astype(np.uint16) b1 = b[:, 1].astype(np.uint16) b2 = b[:, 2].astype(np.uint16) p0 = (b0 << 4) | (b1 & 0x0F) p1 = (b2 << 4) | (b1 >> 4) out = np.empty(height * width, dtype=np.uint16) out[0::2] = p0 out[1::2] = p1 return out.reshape(height, width) # ── Mono10p (PFNC LSB-first, 5 bytes → 4 pixels) ────────────────────── if fmt == "Mono10p": b = raw.reshape(-1, 5) b = b.astype(np.uint16) p = np.empty((len(b), 4), dtype=np.uint16) p[:, 0] = b[:, 0] | ((b[:, 1] & 0x03) << 8) p[:, 1] = (b[:, 1] >> 2) | ((b[:, 2] & 0x0F) << 6) p[:, 2] = (b[:, 2] >> 4) | ((b[:, 3] & 0x3F) << 4) p[:, 3] = (b[:, 3] >> 6) | (b[:, 4] << 2) return p.reshape(height, width) # ── Mono10Packed (Lucid MSB-first, 5 bytes → 4 pixels) ──────────────── if fmt == "Mono10Packed": b = raw.reshape(-1, 5) b = b.astype(np.uint16) p = np.empty((len(b), 4), dtype=np.uint16) p[:, 0] = (b[:, 0] << 2) | (b[:, 1] >> 6) p[:, 1] = ((b[:, 1] & 0x3F) << 4) | (b[:, 2] >> 4) p[:, 2] = ((b[:, 2] & 0x0F) << 6) | (b[:, 3] >> 2) p[:, 3] = ((b[:, 3] & 0x03) << 8) | b[:, 4] return p.reshape(height, width) # ── RGB8Packed (3 bytes per pixel, BGR order from camera) ───────────── if fmt == "RGB8Packed": return raw.reshape(height, width, 3) raise ValueError(f"Unsupported pixel_format: {fmt}") # ── Usage ───────────────────────────────────────────────────────────────── with open("metadata.json") as f: meta = json.load(f) frame = load_raw_frame("frame_000001.raw", meta) print(frame.dtype, frame.shape, frame.max())

Loading All Raw Frames

import os, glob, numpy as np, json with open("metadata.json") as f: meta = json.load(f) frame_files = sorted(glob.glob("frame_*.raw")) # Pre-allocate: all frames as a single array H, W = meta["height"], meta["width"] stack = np.empty((len(frame_files), H, W), dtype=np.uint16) for i, path in enumerate(frame_files): stack[i] = load_raw_frame(path, meta) # using function above print(stack.shape, stack.dtype)

MATLAB — Loading Raw Frames

% Read metadata fid = fopen('metadata.json'); meta = jsondecode(fread(fid, '*char')'); fclose(fid); W = meta.width; H = meta.height; fmt = meta.pixel_format; bpp = meta.bits_per_pixel; % Non-packed formats (Mono8, Mono12, Mono16) fid = fopen('frame_000001.raw', 'rb'); if bpp == 8 frame = fread(fid, [W H], 'uint8=>uint8')'; else frame = fread(fid, [W H], 'uint16=>uint16')'; % little-endian uint16 end fclose(fid); % Mono12p unpacking in MATLAB if strcmp(fmt, 'Mono12p') raw = fread(fopen('frame_000001.raw','rb'), inf, 'uint8=>uint16'); b = reshape(raw, 3, []); % 3 rows: b0, b1, b2 per pixel-pair p0 = b(1,:) + bitshift(bitand(b(2,:), uint16(0x0F)), 8); p1 = bitshift(b(2,:), -4) + bitshift(b(3,:), 4); flat = zeros(1, H*W, 'uint16'); flat(1:2:end) = p0; flat(2:2:end) = p1; frame = reshape(flat, W, H)'; end

Field Correction in Python

import tifffile, numpy as np dark = tifffile.imread("dark_field_mean.tiff").astype(np.float64) white = tifffile.imread("white_field_mean.tiff").astype(np.float64) denom = white - dark denom[denom == 0] = 1 # guard against dead pixels def correct(frame): """Apply flat-field correction. Returns float64 in [0, 1].""" return np.clip((frame.astype(np.float64) - dark) / denom, 0.0, 1.0) # Apply to an entire stack stack = tifffile.imread("stack.tiff") corrected = np.stack([correct(f) for f in stack])

Packed Format Bit Layouts (reference)

The two 12-bit packed formats differ only in which nibble comes first. Both pack two 12-bit pixel values into three bytes labelled b0, b1, b2:

Format b0 b1[3:0] (low nibble) b1[7:4] (high nibble) b2
Mono12p pix0[7:0] pix0[11:8] pix1[3:0] pix1[11:4]
Mono12Packed pix0[11:4] pix0[3:0] pix1[11:8] pix1[7:0]

The Mono10p / Mono10Packed formats use 5 bytes per 4 pixels. The decode formulas are in the Python loader above. Both layouts are LSB-first (Mono10p) or MSB-first (Mono10Packed) analogues of the 12-bit variants.

Pinned Parameters Reference

These are the GenICam node names most commonly pinned to the main panel. Pin any node by clicking the ★ icon next to it in the Advanced Parameters dialog.

Node name What it controls (plain language) Typical value
TriggerMode Hardware trigger on/off. On = camera waits for an external electrical pulse on the trigger line before capturing each frame. Off = camera free-runs at the set frame rate. On
TriggerSource Which GPIO input line the camera listens to for the frame trigger pulse. Line0 or Line2
TriggerActivation Whether the trigger fires on the rising or falling edge of the input pulse. RisingEdge
AcquisitionFrameRateEnable Must be true to make AcquisitionFrameRate writable. Leave false when using external triggering — the node then becomes read-only and reports the sensor's current maximum rate given the active resolution and bit depth. false (external trigger); true (internal)
AcquisitionFrameRate When AcquisitionFrameRateEnable is false: read-only, reports the theoretical maximum for the current sensor config — this is the ceiling for external trigger pulses. When true: writable, sets the internal trigger rate. For external triggering, ensure your trigger source runs a few Hz below this ceiling so every pulse is accepted. Read-only @ 82 Hz (ext. trigger); set to 82 Hz (internal)
ExposureTime How long the sensor integrates light for each frame, in microseconds. Must be less than the frame period (1 / frame rate). For scintillation capture from a ~20 µs quasi-CW x-ray pulse, the light event is over in tens of nanoseconds — longer exposure does not increase signal and only widens the integration window for dark current and stray light. Keep exposure short; frame rate reliability is the binding constraint, not brightness. < 11,700 µs at 82 Hz; keep as short as the camera allows
Gain Electronic amplification of the sensor signal, in dB. Higher gain increases brightness but also amplifies read noise. In practice, full beam is usually too bright at zero gain — pixel saturation is the more common problem. Keep gain ≤ 24 dB (the low-gain mode boundary; above 24 dB the camera switches to a noisier high-gain mode). The primary brightness control is the undulator gap: open it to reduce flux and prevent saturation, close it to increase photon counts. Set gain last, after the undulator gap is dialed in. 0–24 dB (stay in low-gain mode); tune undulator gap first
PixelFormat Bit depth and packing of the pixel data. Mono8 = 8 bits/pixel (fast, low dynamic range). Mono12 = 12 bits stored in 16 bits (better dynamic range). Mono12Packed = 12 bits tightly packed (higher throughput than Mono12). Mono12 or Mono8
Width / Height Active image width and height in pixels. Reducing these (ROI) cuts data throughput proportionally, enabling higher frame rates. As required
OffsetX / OffsetY Top-left corner of the active ROI in sensor pixels. Use Draw ROI in the preview window to set these graphically. Centred on region of interest
BinningHorizontal / BinningVertical Combines N×N neighboring pixels into one output pixel. Reduces resolution but increases SNR and drastically reduces data throughput (2×2 = ¼ pixels). Values: 1 (off), 2, 4. 1 (full res) or 2 (for high speed)
ChunkModeActive Enables per-frame metadata (gain, exposure, GPIO states, timestamps) embedded in each frame. Required for frame_data.csv to be populated. Set once and save to Custom config. true

Scope & Event Trigger Timing

Precise sub-frame event timing is recovered by combining the camera's per-frame GPIO state log with oscilloscope measurements of the trigger signals. This is the standard workflow for relating an external event (e.g., a stimulus, valve open, LED flash) to the exact frame in which it occurred.

Hardware setup

  • Scope 1 is the oscilloscope used for this measurement — located just outside B station.
  • Channel A: Event trigger signal (the stimulus or external event).
  • Channel B: Camera frame trigger (the pulse that clocks each frame).
  • Channel C (optional): Exposure Active output from the camera GPIO, confirming the camera is integrating during the expected window.
  • Use ScopeControlv3.py (use Tools -> Scope Control Software menu bar button in the main window) to automate scope readout and saving.

Analysis approach

  1. From frame_data.csv, identify the frame(s) where line_status_all shows the event input line was high — these are the frames captured while the event was active.
  2. From the oscilloscope, read the time difference Δt between the event trigger rising edge and the next camera frame trigger falling edge after the event.
  3. The event occurred at time −Δt relative to the start of the first frame tagged as active. If Δt is small, the event happened just before that frame; if Δt is close to one frame period, the event happened just after the previous frame trigger.
  4. Cross-check using the camera's hardware timestamp_ns differences in frame_data.csv to confirm the inter-frame interval is consistent with the expected frame rate.
Why this works: The camera accepts an external frame trigger and, simultaneously, monitors a separate event trigger input line. Each frame's chunk data records the state of all GPIO lines at acquisition time — so you know which frame(s) overlap with the event. The oscilloscope provides the fine-grained sub-frame timing that the camera's frame rate alone cannot resolve.

Optical Adjustments

The imaging chain consists of the scintillator, a folding mirror, and the camera lens. Alignment adjustments fall into four categories below. Most sessions require no changes — read each warning before touching anything.

Moving the Camera Relative to the Beam

Camera position is controlled via the EPICS B-station Experimental Table motors.

  • Z axis (35idb:m1) — positive direction is inboard.
  • Y axis (35idb:m3, m6, m4) — positive direction is up.
Note: When moving in Y, keep all three Y motors (m3, m6, m4) moving by the same amount in the same direction. Moving them unevenly can bind the table and make it difficult to recover.

Moving the Scintillator

The scintillator translation stage is controlled from the detector laptop:

Remote Desktop: xxx.xxx.xxx.74  |  Username: dcs\detector-b  |  Password: (standard lab password)

The Conex-CC controllers appear on COM3 (X) and COM4 (Y):

  • X — moves the scintillator holder laterally.
  • Y — moves the scintillator toward or away from the lens (focus). Move Y slowly — it should already be close to correct, and the stage can crash at high values (approximately 25 mm).
Use relative (step) moves only — do not use absolute positioning. Absolute moves fail frequently with these controllers. Always issue small relative steps.
If the controllers become disconnected: they must be re-initialized before use. Click Initialize repeatedly until the stage finds home. After re-initializing, set the speed from the default (2.5) down to 0.5 for more reliable operation.

Adjusting Scintillator Angle

Scintillator tilt is adjusted from the same detector laptop (xxx.xxx.xxx.74, dcs\detector-b, standard password) using the Thorlabs Kinesis software:

  • M1 (horizontal knob) — rotates about the Y-axis of the scintillator mount.
  • M2 (vertical knob) — rotates about the X-axis of the scintillator mount.

The goal is to make the scintillator face planar with the image plane so the entire field can be brought into focus simultaneously.

Adjusting the Folding Mirror Angle

The folding mirror is controlled via New Focus Picomotor software, accessible from either this PC or the detector laptop (the controller is on Ethernet, so either works):

  • M1 — horizontal tilt.
  • M2 — axis tilt (alignment).
  • M3 — vertical tilt.
Do not adjust the folding mirror unless absolutely necessary. The Picomotors are very slow to align and extremely sensitive — small changes are slow to recover from and will affect the focal plane of the optics. Think twice before changing any of these values.
